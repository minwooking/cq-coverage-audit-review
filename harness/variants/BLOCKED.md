# 변이 생성 — 중단 상태와 재개 방법

## 상태

**미완료.** 6개 변이(A–F) 그래프와 렌더링 뷰는 아직 없다.

완료된 것:
- `README.md` — 변이 A–F 정의. `main.tex`의 변이 표에서 가져온 것이며 새로 만든 정의가 아니다.
  B′는 일곱 번째 Brick 변이가 아니라 2차 도메인의 복구 대조다.
- `package_variants.py` — 매니페스트/해시 포장 스크립트
- `_work/atomic_chunks.json` — 1,985 청크
- `_work/triples.json` — **6,004 정제 삼중항** (약 32분 소요, 재사용 가능)

남은 단계: `build` → `split` → `build-a` → `build-c` → `refine-d` → `build-d`
→ `select-standards` → `build-e` → `build-f` → 포장

## 왜 멈췄나 — 메모리

파이프라인이 무거워서가 아니다. **장비에 여유 메모리가 없다.**

| 항목 | 값 |
|---|---|
| 전체 메모리 | 121 GB (GPU와 공유하는 통합 메모리) |
| 사용 중 | 114 GB |
| 가용 | 약 6–7 GB |
| 스왑 | 63 GB 중 34 GB 사용 |
| 서빙 모델(vLLM, 262k 컨텍스트)이 잡은 GPU 메모리 | **101 GB** |
| 모든 프로세스의 실제 RSS 합계 | **12.5 GB** |

RSS 합계가 12.5 GB인데 사용량이 114 GB인 이유는 통합 메모리 구조이기 때문이다.
서빙 모델이 잡은 101 GB가 시스템 메모리에서 그대로 빠진다.

`build` 단계를 두 번 시도했고 두 번 다 시스템 저메모리 보호로 종료됐다.
**추론 엔드포인트 자체는 정상이다** — 큐도 비어 있고 삼중항 단계는 이 장비에서 완주했다.

## 재개 방법 — 셋 중 하나

1. **서빙을 잠시 내린다.** 약 100 GB가 풀려 파이프라인이 무리 없이 돈다.
   단 다른 세션이 같은 모델을 쓰고 있을 수 있으므로 **사람이 판단해야 한다.**
   내린 뒤 아래 스크립트를 돌리고, 끝나면 다시 올린다.
2. **다른 장비에서 돌린다.** 파이프라인은 `triples.json`까지 끝나 있으므로
   `_work/`를 옮기면 남은 단계만 실행하면 된다.
3. **여유가 생길 때까지 기다렸다 이어서 돌린다.** 아래 스크립트는 이미 만들어진
   산출물을 건너뛰므로 몇 번 끊겨도 처음부터 하지 않는다.

재개 스크립트(이어달리기, 완료 단계 자동 건너뜀):

    bash paper/access2026/harness/variants/build_rest.sh

또는 `README.md`의 재현 명령을 `build`부터 순서대로 직접 실행한다.
환경변수 세 개(`CHUNKTOGRAPH_LLM_BASE_URL`, `_MODEL`, `_API_KEY`)를 먼저 export할 것.

## 이 산출물이 왜 필요한가

`run_holdout.py`는 등록된 252셀(216 primary + 24 ablated + 12 preserved)을 계획하며,
변이 매니페스트가 없으면 **가짜 변이를 만들지 않고 즉시 실패한다.**
즉 이 디렉토리가 채워지기 전에는 정식 holdout을 돌릴 수 없다.

## 제출 전 반드시

여기서 만들어질 산출물은 로컬 `qwen-next-flash`로 생성되므로 `SIMULATED: true`가 붙는다.
**사전등록된 판정자·모델로 재생성하기 전에는 원고 결과로 쓸 수 없다.**
